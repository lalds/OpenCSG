# RemoveVerticesInMiddleOfPlane: первый проход Optimize

Перенесён внешний проход `TriangleMesh::RemoveVerticesInMiddleOfPlane`,
macOS x86_64 RealtimeCSG 1.559, `0x33112..0x331ae`.
SHA-256 источника:
`26789e84b0c11376582662bf1d53ed21a65c68d57449efb607070b266cb61a7d`.
Реализация — `native/recovered/plane_vertex_pass.cpp`, интерфейс —
`recovered_mesh_optimization.h`. Windows DLL пока не проверена.

Это первый из двух последовательных проходов исходного Optimize.
[Второй проход и совместный Optimize](two-surface-pass.ru.md) теперь также
перенесены и проверены отдельно; отбор кандидатов описан в своём документе.

## Исходный порядок действий

1. Очищаются размеры removedTriangles и removedVertices в OptimizationContext.
   Остальные четыре scratch-вектора и байты старой ёмкости сохраняются.
2. Вершины посещаются по возрастанию индекса. Для каждой вызывается
   [RemoveVertexInMiddleOfPlane](plane-vertex-removal.ru.md).
   Его bool не проверяется: двухвершинная ветвь возвращает false после мутаций.
   Удалённые записи пока остаются в буферах, поэтому обход использует
   исходный порядок индексов, а последующие удаления видят обновлённую топологию.
3. По `0x331a8` выполняется хвостовой переход в
   [CleanUpRemovedVertices](mesh-cleanup.ru.md) (`0x32b82`). Списки удалений
   сортируются, записи уплотняются и ссылки пересчитываются один раз в конце.

Native brushIndex в этом проходе не используется. Переносимый API вместо
глобальных допущений принимает явные surfaces/planeCount, context и группы.
Сохраняются исходные особенности уплотнения, включая уже описанные случаи,
когда vertexCount не уменьшается после исчерпания хвостового поиска.

## Граница открытой поверхности

Helper одной вершины требует действующего внешнего twin у каждой стороны
собираемой границы. Поэтому внутреннее положение вершины в плоской сетке
ещё не означает возможность удаления: если её веер касается открытого края,
оригинал отказывает. Например, все четыре внутренние вершины открытой сетки
из 3×3 ячеек остаются на месте в исследованном проходе.

Если ту же сетку замкнуть снизу пирамидой, у её периметра появляются внешние
соседи. Четыре внутренние вершины верхней плоскости уже удаляются.
Это поведение оригинала воспроизведено; проверка соседей не ослаблялась
ради ожидаемого результата на открытом меше.

## Транзакция переносимого интерфейса

Последовательный вызов атомарных helpers недостаточен для атомарности всего
прохода: поздняя ошибка могла бы оставить раннее объединение BrushEdge groups
в исходных буферах. Здесь mesh, шесть списков context и три массива групп
выполняются на полных рабочих копиях.

Группы сохраняют раздельные копии refs, triangle handles и connections
с исходными ёмкостями. Даже для нулевой ёмкости рабочие backing pointers
различимы. После перестановок и удалений восстанавливается соответствие
между рабочими дескрипторами и оригинальными буферами владельцев.
До окончания вычислений и проверки этого соответствия исходная память
не меняется. При успехе возвращаются исходные caller-owned pointers
в соответствующем новом порядке, включая retired slots с нулевыми размерами.
Владение выделениями не пересекает API.

Копируются полные исходные активные mesh-буферы, поэтому сохраняются и
хвостовые записи после уплотнения; свободная ёмкость за пределами исходных
triangleCount/vertexCount не трогается. Context и storage групп сохраняют
также байты неиспользуемой ёмкости переносимых буферов.

C ABI `rcsg_recovered_remove_plane_vertices` возвращает 0 при успехе,
-1 для недопустимых входов, -2 для нехватки ёмкости, -3 для прочих ошибок.
Ошибка сохраняет mesh, context, все группы, их буферы и groupCount.
Все изменяемые буферы должны быть раздельными. Проход предназначен для стадии
до построения world/gap-ссылок: их отдельные буферы не пересчитываются.

## Сравнение с оригиналом

`tools/compare_plane_vertex_pass.py` исполняет исходный внешний проход вместе
с helpers обхода, триангуляции, объединения групп и уплотнения, без изменения
их машинных инструкций. Проверяется SHA-256; страницы кода RX, данных RW.
Внешний импорт libc++ сортировки знаковых int обслуживает host-callback
с тем же отсортированным результатом. Это замена импорта, а не проверка
внутренней реализации исходного sort. Выделения для векторов и групп
отслеживаются; исходные перестановки и освобождения исполняются.

Seed 1559, 5 000 входов:

- 36 108 удалённых треугольников;
- уменьшение vertexCount суммарно на 18 054;
- 2 368 удалённых групп;
- 3 262 набора с несколькими удалениями вершин;
- 1 931 набор с замкнутой сетчатой компонентой;
- 495 пустых входов;
- ноль расхождений.

Набор включает открытые сетки, замкнутые тела с плоской сетчатой верхней
гранью, компоненты с двухвершинным вырождением, изменения меток поверхности,
повороты и масштабирование. Индексы треугольников и вершин перемешиваются,
углы каждой записи независимо поворачиваются. Неизвестные поля и исходные
нормали углов заполнены произвольными битами.
У контекста заранее есть ёмкость; native-пути её увеличения не покрыты.
Часть входов объединяет несколько раздельных компонент, поэтому наличие
замкнутой сетчатой компоненты не означает замкнутость всего тестового меша.

Сравниваются все байты буферов треугольников и вершин, включая свободную
ёмкость, metadata/counts mesh, все шесть context-векторов с хвостовыми байтами,
активные группы и их три списка. Теперь проверяются последовательные удаления
на одном изменяемом меше, а не только независимые вызовы для одной вершины.

## Самостоятельный тест и оставшаяся работа

Девятнадцатый CTest использует замкнутое тело с верхней сеткой 3×3 и
пирамидальной нижней частью. Четыре удаления дают 22 треугольника вместо 30
и 13 вершин вместо 17; объём остаётся 3, все twins действуют и взаимны.
Старые списки удалений заранее заполнены недействительными индексами:
проверяется их очистка перед новым проходом.

Другой сценарий сначала объединяет группы в двухвершинной компоненте,
затем исчерпывает ёмкость при обработке следующей компоненты. Проверяется
полный откат mesh/context/groups. После увеличения ёмкости проход завершается;
тест проверяет переставленные исходные pointers активных и retired групп.
Также покрыты пустой mesh и группы с нулевыми ёмкостями/null storage.
Все 19 CTest проходят обычную сборку и ASan/UBSan
(`ASAN_OPTIONS=detect_leaks=0`).

```sh
cmake --build /tmp/realtime-csg-recovery/build
ctest --test-dir /tmp/realtime-csg-recovery/build --output-on-failure
python3 tools/compare_plane_vertex_pass.py --library /tmp/realtime-csg-recovery/build/librealtimecsg_recovered_geometry.so --cases 5000
```

Второй проход и исходная последовательность всего Optimize уже собраны и
[проверены полными вызовами](two-surface-pass.ru.md). Транзакционный слой этого
файла теперь используется обоими проходами и их общим вызовом. Первый проход
по-прежнему сохраняет только исходные активные mesh-буферы; второй и совместный
вариант копируют полные ёмкости для временных новых записей. Автоматическое
включение теперь выполнено в [исследовательской подготовке выпуклых мешей](convex-mesh-preparation.ru.md).
Готовность полной CSG-сцены и Unity ABI этим не заявляется.
