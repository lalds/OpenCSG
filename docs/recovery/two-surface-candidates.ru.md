# Отбор кандидатов во втором проходе Optimize

Исследуется `TriangleMesh::RemoveVertexOnEdgeBetween2Surfaces`, macOS x86_64
RealtimeCSG 1.559, `0x339fe..0x34c44`. SHA-256 источника:
`26789e84b0c11376582662bf1d53ed21a65c68d57449efb607070b266cb61a7d`.
Windows DLL и запуск этого прохода в Unity пока не проверены.

Перенесён **только префикс отбора одной вершины**, `0x33ac3..0x34079`:
`native/recovered/two_surface_candidates.cpp`, интерфейс
`TwoSurfaceVertexCandidate` в `recovered_mesh_optimization.h`.
Это отдельный read-only helper; он не удаляет вершины, не вызывает Swizzle,
не меняет группы или контекст и не заменяет второй проход целиком.
Успех означает лишь допуск к следующим проверкам исходной функции.

## Порядок исходных проверок

1. Handle вершины должен иметь угол 0..2 и индекс существующего треугольника;
   отрицательная поверхность начального треугольника отклоняется.
2. Обход `previous(twin(h))` идёт до первого изменения пары
   `(surfaceIndex, categorizationState)`. Полностью однородный веер отклоняется.
3. Вторая область обходится до изменения её пары. Следующая пара должна
   совпасть с первой. Поэтому две области могут иметь одну поверхность,
   но разные состояния. Флаги треугольников здесь **не сравниваются**.
4. Оставшаяся часть первой области проверяется до исходного handle.
   Исходник неожиданно допускает отсутствующего соседа в этом третьем обходе;
   первые два обхода в таком случае отказывают. Это не доказательство
   допустимости открытого меша для остальной части Optimize.
5. Сохраняются два handle непосредственно перед переходами между областями.
   `X` — вершина предыдущего угла первого handle, `C` — его текущая вершина,
   `Y` — вершина предыдущего угла второго handle. Проверяется
   `dot(normalize(X-C), normalize(X-Y)) >= 0.9999998807907104f`.

Разности вычисляются в float. Для нормализации исходник переводит компоненты
в double, вычисляет длину и обратную длину, умножает и округляет компоненты
обратно в float. Dot снова считается в float. Упорядоченный допуск отклоняет NaN.
Это не симметричная проверка угла двух лучей из C: второй вектор начинается в Y.

Есть наблюдаемая зависимость вырождений от начальной области. Если X=C,
нормализация первого вектора даёт NaN и отказ. Если при другом исходном handle
совпадающая с C точка окажется Y, оба вектора могут совпасть и допуск проходит.
Вырождение не заменялось дополнительным универсальным отказом.

Portable helper проверяет размеры views и индексы читаемых позиций.
Бесконечные циклы некорректной топологии ограничиваются с исключением;
исходный код такого ограничения не имеет. Изменяемый результат должен быть
отделён от mesh storage; он записывается только при успехе. C ABI:
`rcsg_recovered_find_two_surface_candidate`: 1 кандидат, 0 исходный отказ,
-1 недопустимый ввод, -3 прочая ошибка.

## Сравнение ограниченного участка с машинным кодом

`tools/compare_two_surface_candidates.py` использует тот же hash-pinned
бинарник и загрузчик исследовательского oracle. **Два перехода перехвачены**:
при достижении `0x3407f` возвращаются два граничных handle и 1;
при достижении `0x34bf6` возвращается 0. Выполнение следующих вершин,
мутаций и уплотнения не производится. Инструкции самих обходов и численной
проверки между этими границами не изменены. Завершённый static guard задан
заранее, диагностический callback отсутствует. Страницы кода после установки
перехватов RX, данных RW.

Для выбора конкретной вершины oracle передаётся копия дескриптора с
`vertexCount=vertex+1`: внешний проход начинает с последней вершины.
Позиции остаются в полном выделенном буфере; исходный префикс не сверяет их
индексы с этим счётчиком. Portable helper получает полный корректный дескриптор.
Сравниваются решение, оба handle, сохранение результата при отказе и все
исходные байты меша. Контекст префикса содержит живые пустые векторы.

Seed 1559, 5 000 входов: **1 423 кандидата, 3 577 отказов, ноль расхождений**.
Веера из 2..22 треугольников, перемешанные индексы вершин/треугольников,
независимые повороты углов, повороты и масштабы геометрии, произвольные флаги
и неизвестные поля. Есть единая область, три поверхности, чередующиеся области,
разные состояния одной поверхности, открытые соседи, недействительные стартовые
handles, пороговые изгибы, совпадающие точки, NaN и Infinity.

Двадцатый CTest отдельно проверяет разбиение по состоянию при одной поверхности,
неучёт флагов, отказ при чередующихся областях и изгибе, зависимость вырождения
от начальной области, NaN, отсутствие мутаций и ограничение некорректного цикла.
Все 20 CTest проходят обычную сборку и ASan/UBSan (`detect_leaks=0`).

```sh
cmake --build /tmp/realtime-csg-recovery/build
ctest --test-dir /tmp/realtime-csg-recovery/build --output-on-failure
python3 tools/compare_two_surface_candidates.py --library /tmp/realtime-csg-recovery/build/librealtimecsg_recovered_geometry.so --cases 5000
```

## Карта остальной части функции

Теперь она [перенесена и проверена полными вызовами](two-surface-pass.ru.md).
Ниже адресная карта; сам prefix-oracle по-прежнему проверяет только отбор:

- `0x339fe..0x33ac3`: очистка двух списков удалений, обход исходных вершин
  по убыванию индекса; добавленные позже вершины не становятся новыми итерациями.
- `0x3407f..0x340c2`: предварительный рост triangle/vertex capacities.
  Он происходит ещё до последующих отказов; поведение ёмкостей нужно учитывать
  отдельно от изменений геометрии.
- `0x340c2..0x3426f`: проверки соседей через оба граничных twin, согласования
  поверхностей/состояний и общих endpoint-индексов, особый двухтреугольный случай.
- `0x3426f..0x34453`: дополнительные проверки длины, вырождения и ориентации
  относительно исходной плоскости; часть допусков похожа на Swizzle,
  но ветви отношения dot к произведению квадратов длин отличаются.
- `0x34453..0x345e8`: выбор между Swizzle, повторным отбором текущей вершины
  после Swizzle и вызовом RemoveVertexInMiddleOfPlane.
- `0x345e8..0x34bf6`: два временных треугольника, MergeBrushIndices для четырёх
  тегов, перестройка twins, дублирование позиции/обхода вершины и два вызова
  RemoveVertexInMiddleOfPlane. Handle копии заново устанавливается в r11d
  по `0x34990..0x34993`; он не зависит от значения регистра после merge.
- `0x34bf6..0x34c44`: переход к следующей исходной вершине и хвостовой вызов
  CleanUpRemovedVertices.

Оставшиеся проверки и ветви перестройки проверяются отдельным полным oracle.
Результаты одного этого префикса не считаются проверкой полного Optimize.
